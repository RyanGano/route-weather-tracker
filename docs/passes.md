# Pass data reference & validation

This is the source-of-truth reference for **what data each pass shows, where it
comes from, and how to re-verify it** without redoing the original fact-finding.

- The pass list itself lives in
  [`PassRegistry.cs`](../route-weather-tracker-service/Data/PassRegistry.cs)
  (coordinates, elevation, highway, state, official URL).
- The machine-checked accuracy report is
  [`passes-validation.md`](./passes-validation.md), regenerated by
  [`tools/validate_passes.py`](../tools/validate_passes.py).
- The planning history (per-state endpoints, future integrations) is in
  [`STATES.md`](../STATES.md). Where that doc and `PassRegistry.cs` disagree on a
  coordinate, **the registry + validation report win** — STATES.md is historical.

## How to re-validate (do this when adding/editing passes)

```bash
python tools/validate_passes.py            # full check, writes docs/passes-validation.md
python tools/validate_passes.py --no-url   # elevation only (fast, offline-ish)
```

What it checks, using only key-free public APIs:

1. **Coordinate sanity** — compares each pass's `ElevationFeet` against the real
   terrain elevation at its `(lat, lon)` from the [Open-Meteo elevation
   API](https://open-meteo.com/en/docs/elevation-api). A Δ larger than the
   tolerance (default ±500 ft) means the coordinate is probably off the summit.
   This is how all the coordinate fixes in this repo were found and verified.
2. **Official URL liveness** — HTTP status of each `OfficialUrl`.

To find a **correct** coordinate for a flagged pass, geocode it via OSM Nominatim
(`https://nominatim.openstreetmap.org/search?q=<Pass Name>,<State>&format=json`)
and accept the result only when Open-Meteo elevation at that point matches the
registry's summit figure. Respect Nominatim's 1 req/sec limit and send a
descriptive `User-Agent`.

### Known approximate coordinates (intentionally not "fixed")

These stay flagged by the validator because they are corridors/ridges rather than
a single signed summit, or the name conflates two places. They are close enough
for routing and (where applicable) camera proximity:

| Pass | Why it's approximate |
|------|----------------------|
| Mt. Shasta Summit (CA, I-5) | "Summit" figure (3,540 ft) is lower than the I-5 high point near the stored point; camera still matches "South Weed" correctly. |
| Sardine Canyon (UT, US-91) | Cameras are matched by name, not coordinate; the divide vs. canyon-floor elevation differs. |
| UT-153 Summit (UT) | Tushar Mountains corridor; no single signed summit. |
| Veyo / Black Ridge (UT, I-15) | Name conflates Veyo (SR-18) and the I-15 Black Ridge climb. |
| Clinch Mountain (TN, US-11W) | Coordinate is on the actual US-11W ridge crossing; the 3,074 ft figure is the ridge crest, the road gap is lower. |

## Data sources per state

Legend: **Conditions** = official DOT road/restriction data; **Cameras** = live
roadside images; **NWS** = weather + a condition *derived* from weather when no
official source exists (`HasOfficialConditions = false`).

| State | Conditions | Cameras | Live feed in use | Auth |
|-------|-----------|---------|------------------|------|
| WA | ✅ WSDOT | ✅ WSDOT | `wsdot.wa.gov/.../GetMountainPassConditionsAsJSON` | free key (`WsdotApiKey`) |
| ID | ➖ NWS | ✅ (Fourth of July, Lookout) | `511.idaho.gov` camera scrape | none |
| MT | ➖ NWS | ✅ MDT RWIS | `mt.cdn.iteris-atis.com/.../icons.rwis.geojson` | none |
| OR | ➖ NWS | ❌ none yet | — (ODOT TripCheck pending) | none |
| CO | ➖ NWS | ❌ none yet | — (CDOT COtrip pending, needs key) | key |
| **CA** | ➖ NWS | ✅ **Caltrans CCTV** | `cwwp2.dot.ca.gov/data/dN/cctv/cctvStatusDNN.json` | none |
| WY | ➖ NWS | ❌ none yet | — (WYDOT ArcGIS pending) | none |
| UT | ➖ NWS | ✅ UDOT | `udotcameras.com/...processed.geojson` | none |
| NV | ➖ NWS | ❌ none yet | — (NDOT ArcGIS pending) | none |
| NM | ➖ NWS | ✅ NM Roads¹ | `servicev5.nmroads.com/.../GetCameraInfo` | none |
| VA | ➖ NWS | ❌ none yet | — (VDOT 511 pending, needs key) | key |
| NC/TN | ➖ NWS | ❌ none yet | — (NCDOT/TDOT pending) | TN needs key |

¹ The NM Roads API returns `{ "cameraInfo": [ … ] }` (not a bare array), and its
snapshot host `ss.nmroads.com` is **HTTP-only**. HTTP-only snapshots are served to
the HTTPS frontend through the allowlisted proxy `GET /api/cameras/image?url=…`
([`CamerasController`](../route-weather-tracker-service/Controllers/CamerasController.cs),
applied client-side by `proxiedCameraUrl`). Raton, Glorieta, and Tijeras have
cameras within ~2–8 km; Emory and Apache Summit have none within range (~105 km+).

States still showing ❌ cameras are the highest-value next targets. Caltrans (CA)
proves the pattern: a key-free, per-district JSON feed + proximity matching. The
remaining ArcGIS-based states (WY, NV) and ODOT TripCheck (OR) can follow the same
`MontanaPassDataSource` / `CaliforniaPassDataSource` shape — see `STATES.md` for
the documented endpoints.

### California camera coverage (verified)

Implemented in
[`CaliforniaPassDataSource.cs`](../route-weather-tracker-service/Services/CaliforniaPassDataSource.cs).
Each pass queries the Caltrans district feed(s) covering it and returns the two
nearest in-service cameras within 25 km:

| Pass | District feed(s) | Nearest camera |
|------|------------------|----------------|
| Mt. Shasta | D2 | ~2.9 km (I-5 South Weed) |
| Donner | D3 | ~2.7 km (I-80 Castle Peak) |
| Echo Summit | D3 | ~0.5 km (US-50 Echo Summit) |
| Cajon | D8 | ~1.2 km (I-15 @ Jct 138) |
| Tehachapi | D6, D9 | ~2.6 km (SR-58 Summit) |
| Sonora | D10, D9 | ~15.5 km (US-395 @ SR-108 Jct) |
| Tioga | D10, D9 | ~20.8 km (US-395 Conway Summit) |
| Monitor | D10, D9 | none < 25 km (remote seasonal pass) |

> **Maintenance note:** a few data sources keep their own copy of pass
> coordinates for camera proximity (California, Utah, New Mexico, Montana). When
> you change a coordinate in `PassRegistry.cs`, update the matching entry in that
> state's data source too. A future cleanup could have those sources read straight
> from `PassRegistry`.
